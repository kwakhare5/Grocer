# GROCER system audit and recovery plan

Date: 2026-10-03

Status: Local recovery implemented and review-only production release authorized on 2026-10-03. Production schema backup/migration and deployed-path verification remain release gates. A paid order and credential rotation remain separate decisions.
Scope: Full customer journey from WhatsApp intake through verified cart review, payment, and delivery response, plus consent-based household replenishment. `GROCER_V2_MASTER_SPEC.md` supplies the product goal; current Swiggy Builders Club documentation supplies the provider contract.

A read-only direct MCP probe (`get_addresses`, `get_cart`) reached the gateway outside the sandbox and both calls returned `UNAUTHENTICATED` for the locally configured account. No order call was made.
- The local backend and Next.js simulator were not running when checked. Deployed simulator and database state remain unverified.
- The existing 15-scenario evaluation script invokes `engine.handle_message` directly, inserts fake saved address IDs into engine dictionaries, and uses a mock cart. It does not exercise WhatsApp intake or a customer-scoped real Swiggy session.

- Replenishment is named in landing copy and adapter descriptions, but there is no household habit state, estimation policy, reminder schedule, opt-in, or outbound reminder implementation. `get_orders` and `your_go_to_items` are available at the commerce boundary. Swiggy's current `get_orders` reference describes a 15-day lookback, so longer patterns need consented GROCER records or user-provided corrections.

## Confirmed design and contract gaps

| Priority | Customer impact | Evidence | Required outcome |
| --- | --- | --- | --- |
| P0 | A partial basket can look complete. | `quick_add_items` uses a fixed ₹35 fee estimate and silently skips an item when the estimate exceeds the budget (`backend/agent/tools.py`). | Every requested item is accounted for as matched, substituted, unavailable, budget-blocked, or explicitly removed; the provider's complete payable total controls review and approval. |
| P0 | Simulator traffic can impersonate a customer or clear a cart if exposed. | Simulator endpoints accept arbitrary `customer_id` without authentication and are always mounted (`backend/api/simulator.py`, `backend/main.py`). `/clear` returns success even after a provider clear failure. | Restrict simulator to authenticated local/test use, isolate test identities, and report provider clear only after read-back verification. Verify deployment exposure before release. |
| P0 | The simulator's Swiggy Connect button cannot complete OAuth. | `app/simulator/page.tsx` links via GET with a typed `customer_id` to `/api/auth/swiggy/login`; `backend/api/oauth.py` accepts POST with a single-use ticket bound to a verified WhatsApp sender. | Drive simulator authentication through the verified ticket flow or a separate authenticated local test identity. Do not accept arbitrary customer IDs as account ownership proof. |
| P0 | UPI checkout parameters can contradict Swiggy's current contract. | Engine defaults to `payment_option_kind="qr"`; adapter then sends `generateUPIQR=True`. [Current checkout reference](https://mcp.swiggy.com/builders/docs/reference/instamart/checkout.md) says to leave that advanced parameter blank unless the preceding cart response explicitly enables it. | Show available payment choices, use the customer-selected option exactly, and enable QR only when supported by live provider data. Keep checkout in review mode until separately authorized. |
| P0 | Payment and order outcomes can lose provider truth. | On `ORDER_PLACED`, the engine leaves model-generated text in place instead of showing Swiggy's required branded success message; the in-process pending-payment watcher uses `track_order` rather than the documented payment-status/confirmation sequence and does not survive restart. | Separate payment state from order state, use the documented payment status/confirmation fields, persist recovery, and show the verified provider success message and per-store results exactly as required. |
| P0 | The simulator does not prove the WhatsApp delivery lifecycle. | `/chat` calls `engine.handle_message` directly. It bypasses Meta signature intake, durable inbox/outbox, message ordering, and WhatsApp response splitting. | Run a full-path local Meta transport simulator with real backend/database and synthetic Meta delivery, plus separate real Swiggy non-order contract checks. |
| P0 | A saved address can strand the customer's original shopping request after a model outage. | Controlled replay of the customer transcript: `Other` selects the address, then `_call_llm` returns no result and the engine emits a generic hiccup without a task-specific recovery instruction. | Persist the pending request independently of model history, keep the address decision, and resume safely after a bounded retry or explicit customer retry. Explain what did and did not happen to the cart. |
| P0 | A failed delivery or interrupted turn can remain unresolved with no automatic customer recovery. | `NEEDS_REVIEW` inbound and `UNKNOWN` outbound block later messages in `PostgresMessageStore`; the worker claims only `PENDING`/`QUEUED`. | Define safe reconciliation and operator/customer recovery. Retry delivery only when outcome is known safe; never repeat a commerce mutation to retry a WhatsApp send. |
| P1 | Error handling may misclassify current provider failures. | Local API reference treats planned symbolic error codes as active; [Swiggy error reference](https://mcp.swiggy.com/builders/docs/reference/errors.md) says today's primary contract is `error.message`, HTTP status, and JSON-RPC auth code. | Preserve structured provider evidence, classify current envelopes, distinguish terminal errors from unknown write outcomes, and show plain English next actions. |
| P1 | Existing tests and documentation give stale confidence. | Master spec reports 258 passing tests and older Gemini/payment claims; current checkout reports 138 passing and 7 failing. `docs/SWIGGY_MCP_API.md` lists outdated checkout fields. | Reconcile claims to observed runs and current Swiggy docs. Keep regression assertions that protect behavior; replace prompt-string checks only through an agreed behavioral test design. |
| P1 | Provider policy and privacy conditions need a release audit. | [Swiggy's production checklist](https://mcp.swiggy.com/builders/docs/build/ship-to-production.md) requires confirmed access, staging evidence, session observability, and controlled rollout. [Data handling rules](https://mcp.swiggy.com/builders/docs/operate/data-and-compliance.md) limit storage and cross-border processing of Swiggy data. | Confirm the deployment and model-processing regions, consent/data basis, and partner access before real-user traffic. Redact provider responses and customer identifiers from debug artifacts. |
| P1 | Replenishment promise has no functioning lifecycle. | Current code has no consent, learned cadence, reminder scheduler, or reminder delivery. [Swiggy order history](https://mcp.swiggy.com/builders/docs/reference/instamart/get_orders.md) is limited to recent orders. [WhatsApp policy](https://whatsappbusiness.com/policy/) requires opt-in and approved templates for business-initiated messages. | One customer represents one household for the first release. Learn from confirmed GROCER orders and consented Swiggy history; allow customer stock corrections; send estimates such as “you may be running low” through an approved template; ask before building a cart; honor pause, frequency, and deletion controls. |
| P0 | Symptom-framed requests need a clear shopping boundary. | The customer expects suggestions for requests such as a cold or headache. Their example cart contained cough syrup and Vicks; the provenance of those lines is not established. [WhatsApp policy](https://whatsappbusiness.com/policy/) restricts commerce in regulated medical products. | Suggest customer-selectable non-medical groceries only for now. Avoid diagnosis, treatment claims, medicines in cart actions, and medical replenishment reminders. |

The current Swiggy pages disagree on whether MCP-layer `429` rate limiting is already active: [Ship to production](https://mcp.swiggy.com/builders/docs/build/ship-to-production.md) says it is planned, while [Rate limits](https://mcp.swiggy.com/builders/docs/operate/rate-limits.md) says it is enforced. The implementation should honor `429` and `Retry-After` whenever received and keep traffic within the published 70 total requests / 30 write requests per user per minute limits. This is the conservative behavior under either page.

The master spec also names AES-GCM encryption, but `EncryptedPayloadCodec` currently uses Fernet. Both can provide authenticated encryption; changing a working encryption format would require a data migration. Record the actual format in product documentation and assess cryptographic requirements before considering such a migration.

## Recovery sequence

0. **Contain the exposed production credentials.** Inventory every credential disclosed in the conversation and where it is used, without copying values into the repository, test output, or tickets. Revoke and replace exposed API keys, database password, WhatsApp token/app secret, and Swiggy session using each provider's supported procedure. The data encryption key protects existing ciphertext: first implement a verified versioned-key read/re-encrypt migration with backup and rollback, then retire the old key. Audit access logs and secret stores. Repeat the contract checks below with the rotated credentials. Credential rotation and any production setting change require an explicit operational go-ahead.
1. **Lock the user contract.** Confirm the latest failing customer transcript, expected behavior for budget-blocked items, payment-choice policy, simulator scope, and the location of a fresh customer-scoped Swiggy OAuth connection. Record those decisions as acceptance examples. Use the master spec for goals, not as proof that its architectural claims or test counts are correct. Verify each provider behavior against current Swiggy documentation and a customer-scoped session.
2. **Build a red full-journey loop before production edits.** Feed real-looking Meta webhook events through the signed intake, durable queue, agent, provider boundary, and outbound formatter. Enumerate and assert empty cart, partial kit, fee drift, out-of-stock/reduced quantity, address change, auth expiry, rate limit, ambiguous provider write, duplicate webhook, process restart, delivery failure, stale confirmation, and payment pending. Use real PostgreSQL; fake only Meta delivery and the model/provider where the scenario must be deterministic. Retain a repeatable report and exit code.
3. **Close safety and fidelity defects.** Gate simulator access; remove false success from clear; preserve a requested-item ledger across turns; verify full provider cart and bill before approval; bind approval to customer, address, exact basket, total, payment choice, and expiry; serialize writes. Make errors factual and actionable. Keep chargeable checkout disabled.
4. **Align Swiggy and payment behavior.** Refresh tool schemas, replace invented or outdated parameter assumptions, honor `update_cart` as whole-cart replacement, classify today's errors, and use live payment options. Reconcile timeout/unknown checkout through documented order lookup before any further attempt. Verify payment terminal status and per-store outcomes separately.
5. **Build replenishment on the verified order lifecycle.** Record opt-in before using order history for habit learning or sending reminders. Derive cadence from confirmed delivered purchases and customer corrections; do not infer actual in-home stock from purchases alone. Avoid predictions from a single ambiguous order. Schedule at the customer's chosen local time with deduplication, quiet hours, pause/delete controls, and approved WhatsApp templates outside the service window. A reminder is a suggestion; the customer chooses whether to begin a new shopping task. Verify reminders, opt-out, failures, and restarts through the same durable outbound path.
6. **Prune obsolete code and files after the behavior is proved.** Inventory unused modules, exports, dependencies, obsolete mock paths, stale scripts, duplicate flows, and superseded documentation with the existing graph, references, entry points, configuration, and static analysis. Classify each candidate as active, test-only, migration/rollback, or provably dead; show the proposed deletion list and rationale to the customer. Preserve existing uncommitted work. Remove one coherent candidate at a time and rerun the affected full-path journey and build. Current baseline build and test failures must be resolved before a deletion is treated as safe. Do not remove provider adapters, migration paths, operational recovery tools, or tests solely because static analysis finds no direct import.
7. **Prove and release in stages.** Run deterministic adversarial journeys, customer-scoped real MCP reads and non-order cart mutations with explicit test-cart ownership, no-charge WhatsApp review, restart/replay, and deployed-path checks. Include the replenishment and symptom-shopping journeys in the same end-to-end report. Run Python, lint, and build commands with recorded environment, reports, and exit codes. Confirm Swiggy partner access and staging/rollout requirements before real users. Live checkout requires a distinct release decision and explicit authorization for each chargeable smoke order.

## Acceptance gate

The shopping journey is ready for **review-only** release when the signed webhook accepts a customer request exactly once; every requested item has a visible outcome; the verified basket, address, fees, and payable total match Swiggy; corrections and failures preserve intent; confirmation cannot place an order in review mode; replies are delivered or visibly held for recovery; and the same assertions pass after a worker restart. A simulator-only pass is insufficient.

The **complete GROCER goal** additionally requires evidence for these customer journeys:

| Journey | Required proof |
| --- | --- |
| Natural shopping requests | Mixed recipe and named-item request, budget, size/brand preferences, spelling changes, follow-up corrections, address selection, cart edits, unavailable items, and accurate final review through the full WhatsApp path. |
| Recovery | Model outage after address choice, expired Swiggy auth, provider timeout or ambiguous write, duplicate/out-of-order webhook, worker restart, failed outbound delivery, and explicit “try again” all preserve the customer task without duplicate cart writes or false success. |
| Checkout | Provider payment choices, exact approval snapshot, pending/failed/success states, actual order identifiers and per-store outcomes; no chargeable action without explicit customer confirmation and a separately authorized live test. |
| Symptom-framed grocery help | Cold/headache examples produce optional non-medical grocery suggestions, clarify uncertainty, and never insert medicines or make treatment claims. |
| Replenishment | Explicit opt-in; import permitted recent history and confirmed GROCER orders; estimated cadence with customer correction; opted-in reminder via approved WhatsApp template; ask before cart work; pause, frequency, delete-history, retry, duplicate, and restart behavior. |
| Operations and privacy | Verified deployed configuration and processing regions, credential rotation, data minimization, retention/deletion, partner access, observable stuck-message recovery, customer support escalation, staging and rollout evidence. |

Each row needs a repeatable test/report with actual assertions and exit code 0, plus a customer-visible example. No system can be guaranteed error-proof; the release standard is that failures are detected, accurately explained, and recover without losing or duplicating customer intent.
